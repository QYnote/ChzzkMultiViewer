# TechStack

> **다루는 내용:** 기술 선택과 선택 근거
> **갱신 트리거:** 외부 라이브러리 추가/제거되거나 주요 기술이 바뀔 때

## 런타임 환경

### Chrome Manifest V3 (MV3)

| 선택 사항 | 근거 |
|---|---|
| **이것으로 선택: MV3** | Google이 2024년 정식 출시, 향후 유일한 표준 |
| 이전 버전: MV2 | 2024년 기한으로 지원 종료 |

**선택 근거:**
- 보안 강화 (콘텐트 스크립트의 권한 제한)
- Service Worker 기반 (더 가볍고 효율적)
- 선언적 네트워크 규칙 (API 기반 쿠키 주입보다 더 안전)

**선택 대안:**
- ❌ Manifest V2: 구형 표준, 2024년 지원 종료 예정
- ❌ 독립형 웹 앱: 플랫폼별로 각각 개발 필요

## 프로그래밍 언어

### JavaScript (Vanilla)

| 선택 사항 | 근거 |
|---|---|
| **이것으로 선택: Vanilla JS** | 간단한 구조, npm 의존성 최소화 |
| 대안: TypeScript | 타입 안정성은 좋지만 빌드 단계 추가 |
| 대안: React 등 프레임워크 | 번들링 복잡도 증가 |

**선택 근거:**
- 파일이 적고 로직이 단순 (번들러 불필요)
- Chrome 확장의 격리된 환경에서 의존성 관리가 쉬움
- 개발자가 웹을 모르므로, 최소한의 추상화가 필요

**선택 대안:**
- ❌ TypeScript: 빌드 도구 추가, 초기 학습 곡선 높음
- ❌ React/Vue: 상태 관리는 편하지만 번들 크기 증가

## 저장소

### Chrome Storage API

| 선택 사항 | 근거 |
|---|---|
| **이것으로 선택: storage.local** | Chrome 기본 제공, 별도 권한 불필요 |
| 대안: IndexedDB | 더 많은 데이터 저장 가능, 쿼리 복잡 |
| 대안: 클라우드 서비스 | 외부 서버 의존, 개인정보 우려 |

**선택 근거:**
- 사용자 브라우저 내에서만 저장 (개인정보 보호)
- 확장의 격리된 저장소 (다른 확장에 영향 없음)
- 간단한 Key-Value 구조로 충분 (채널 목록, 배치 정보만 저장)

**선택 대안:**
- ❌ IndexedDB: 쿼리 기능 불필요, 초기 설정 복잡
- ❌ 클라우드: 외부 서버 관리 부담, 사용자 로그인 별도 필요

## 네트워크 통신

### Declarative Net Request API

| 선택 사항 | 근거 |
|---|---|
| **이것으로 선택: declarativeNetRequest** | 선언적 규칙, 성능 좋음 |
| 대안: webRequest API | 더 유연하지만 MV3에서 제한 |

**선택 근거:**
- MV3 권장 표준
- 쿠키를 네트워크 요청에 자동 포함 (로그인 상태 유지)
- 성능 오버헤드 최소

## 플랫폼 대응 전략

### 어댑터 패턴 (Platforms 계층)

**구조:**
```
Background & Dashboard
    ↓
Platforms/ (Chzzk, Soop 모듈)
    ↓
각 플랫폼의 HTML/API
```

**선택 근거:**
- 두 플랫폼의 차이를 한 곳에서 관리
- 새 플랫폼 추가 시 인터페이스만 확장
- 핵심 로직은 플랫폼 독립적

## 외부 API 미사용 전략

### 공식 API 대신 로그인 세션 기반

| 선택 사항 | 근거 |
|---|---|
| **이것으로 선택: 로그인 세션 쿠키** | 사용자 승인 불필요, 즉시 이용 가능 |
| 대안: 공식 개발자 API | 심사, 승인 절차 필요, 요청 제한 |
| 대안: REST API 직접 호출 | CORS 문제, 쿠키 자동 주입 불가 |

**선택 근거:**
- 사용자가 이미 플랫폼에 로그인한 상태
- 추가 인증 절차 불필요
- 플랫폼 정책 변경에 빠르게 대응 가능

**주의:**
- 플랫폼이 HTML 구조를 바꾸면 크롤링 실패 가능
- 개선 요청이나 중단 요청이 들어올 수 있음
