# Git

> **다루는 내용:** 브랜치를 왜 이렇게 나누는지, 버전 번호를 어떤 기준으로 올리는지
> **갱신 트리거:** 브랜치 전략이나 버전 규칙이 바뀔 때

> 커밋·배포·hotfix를 **실제로 어떤 순서로 실행하는지**는 이 문서에 적지 않는다. 저장소 루트 `CLAUDE.md`의 `Git 관리 전략`을 따른다.

## 본문

### 브랜치 구조

| 브랜치 | 어디서 파생 | 역할 |
|---|---|---|
| `master` | — | 배포 전용. 직접 커밋하지 않는다 |
| `develop` | `master` | 모든 개발의 기준. 파생 브랜치가 여기서 시작해 여기로 돌아온다 |
| `feature/기능명` | `develop` | 기능 개발 단위. 소규모 기능도 반드시 만든다 |
| `hotfix/설명` | `master` | 긴급 수정. `master`·`develop` 양쪽에 병합한다 |

**왜 이렇게 나누는가**

- `master`를 배포 전용으로 비워 두면, 언제 받아 가도 동작하는 상태가 보장된다. 긴급 수정을 `develop`이 아니라 `master`에서 따는 이유도 이것이다 — 개발 중인 미완성 변경을 함께 내보내지 않기 위해서다.
- 소규모 기능에도 `feature` 브랜치를 강제하는 이유는, 사용자 확인 전 변경이 `develop`에 섞이면 되돌릴 단위가 사라지기 때문이다.
- `hotfix`를 양쪽에 병합하지 않으면 다음 배포 때 수정이 되돌아간다.

**완료 판단 기준** — 사용자가 테스트 후 정상 동작을 확인한 시점.

### 버전 규칙

| 상황 | 단위 |
|---|---|
| 새 기능이 포함된 배포 | +0.1.0 |
| 버그 수정·문구 정정만 나가는 배포 | +0.0.1 |

기준은 **어느 브랜치에서 작업했는지가 아니라 사용자에게 새로 생긴 것이 있는지**다. `feature` 브랜치에서 한 작업이라도 버그 수정뿐이면 +0.0.1이다. 한 배포에 기능과 수정이 섞여 있으면 +0.1.0이다.

버전을 올리는 시점은 배포할 때 한 번뿐이다. 기능을 개발하는 동안에는 올리지 않는다.
