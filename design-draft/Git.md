# Git

> **다루는 내용:** Git 브랜치 전략 · 커밋/배포 절차 · 버전 규칙
> **갱신 트리거:** 브랜치 전략이나 배포 절차가 바뀔 때

## 본문

### 브랜치 구조

| 브랜치 | 역할 |
|---|---|
| `master` | 배포 전용. 직접 커밋하지 않는다 |
| `hotfix/설명` | `master`에서 파생, 긴급 수정 후 `master`·`develop` 양쪽에 병합 |
| `develop` | `master`에서 파생, 모든 개발의 기준 브랜치. 모든 파생 브랜치가 여기서 시작해 여기로 병합됨 |
| `feature/기능명` | `develop`에서 파생, 기능 개발 단위. 소규모 기능도 반드시 생성. 완료 시 `develop`에 병합 |

완료 판단 기준: 사용자가 테스트 후 정상 동작을 확인한 시점.

### 커밋 절차 (정상 동작 확인 시)

1. [Overview](Overview.md) 기준으로 이번 작업 개발 내역 보고
2. 확인 후 커밋
3. [README](README.md)의 `업데이트 예정 기능`에서 완료된 항목을 `[x]`로 표시
4. `feature` 브랜치를 `develop`에 병합
5. 병합 완료 후 `feature` 브랜치 삭제

### 버전 규칙

| 상황 | 단위 |
|---|---|
| hotfix 완료 후 배포 | +0.0.1 |
| 일반 기능 개발 배포 | +0.1.0 |

### 배포 절차

**1단계 — 배포 준비**
1. 진행 중인 `feature` 브랜치는 건드리지 않는다
2. `manifest.json`의 `version`을 규칙에 맞게 올린다
3. [README](README.md)의 `업데이트 예정 기능`에서 `[x]` 표시된 항목을 전부 삭제한다
4. [Changelog](Changelog.md)에 새 버전 항목을 추가한다 (사용자가 체감할 수 있는 변화 위주, 내부 구현 용어는 쓰지 않음)
5. `develop` → `master` 병합
6. 병합 내용을 요약 보고하고 push 여부 확인

**2단계 — 푸시**
1. `master`를 `origin/master`에 push
2. 배포 파일(ZIP)을 `master` 기준으로 생성 (자세한 절차는 [Build](Build.md) 참고)

### hotfix 절차

1. `master`에서 `hotfix/설명` 브랜치 생성
2. 긴급 수정 완료
3. `master`에 병합 후 버전 0.0.1 상승
4. `develop`에도 동일하게 병합해 수정 내용 반영
